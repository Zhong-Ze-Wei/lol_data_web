# AI 分析的战队名称口径

AI 表格中的“来源战队”“对手来源战队”“获胜来源战队”表示每条出场或比赛记录保存的队伍标签。它同时覆盖 ScoreGG 已核验记录和未核验历史导入，不能统一称为“单局详情名称”。来源标签可能与历史赛程名称不同，也不等于已核实的当年正式队名。

查询继续按记录标签分组和筛选，不自动合并历史名称，不通过名称推断官方转会或更名。核验标志证明该记录已通过现有来源校验，不额外证明队名在历史日期的正式身份。

例如询问“2016 年已核验 Uzi 在 QG 的比赛”，保存为 `JDG` 的记录不会自动纳入 `QG` 筛选。当前结果可能为空，或名称不在实际记录目录中而需要澄清；这不证明现实中没有这些比赛。本次只修复来源说明，尚未支持按官方历史队名关联查询。

## 本次修复的依据

一次真实问题查询了 2016 年已核验 LPL 比赛中 Uzi、Xiaohu 按记录战队分组的击杀与 MVP 数据。独立 SQL 对照冻结了 112 局、161 次出场，84 项计数、样本、范围和展示检查全部通过。其中 Uzi 的 20 次出场记录保存为 `JDG`。

这 20 局对应 11 个 BO 系列、9 份已归档阶段赛程。同一 `teamID=28` 在赛程中标为 `QG`，在单局详情中标为 `JDG`。对照确认了双方 teamID、BO 编号、Uzi 星位、击杀和 MVP，以及赛程原件哈希与持久化 `source_json` 的一致性，共 140 项来源关联检查。

例如单局 `436` 属于系列 `197`，赛程日期为 `2016-01-31`；赛程的 `teamID_a=28`、`team_short_name_a=QG`，详情的 `red_teamID=28`、`red_name=JDG`。证据证明两个来源的标签不一致。它没有独立证明当年官方队名、组织继承关系或正式转会日期，不能据此建立全局 `QG ↔ JDG` 别名。

本机验收证据位于忽略的 `artifacts/ai-count-samples-live-benchmark.json`、`artifacts/ai-count-samples-live-projection.db` 和 `artifacts/ai-count-samples-team-label-source-audit.json`。人工 NULL、零值和有效样本边界测试与这次真实查询分开保存；上述真实范围没有 NULL 击杀或 MVP，不能冒充真实 NULL 边界验收。

## 修改范围

- AI 业务目录和返回列使用来源战队标题，并在队名、对手、胜方的定义中说明来源边界。
- 查询说明、模型规划和文字解读提示都说明来源名称可能与历史赛程不同；本地解读也把队伍名称标为来源战队。
- SQL、数值、有效样本、实体解析和保存的查询条件保持原口径。数据库、归档原件、采集与普通页面布局未修改。

这次修复通过提示词约束 AI 文字，不增加按名称猜测或重写模型答案的规则。模型解读仍须以查询数据为准，固定的列定义与统计口径始终可核对。

## 后续名称数据修复的边界

现有 `HistorySeries.source_json` 和父阶段原件保存了赛程中的 teamID 与名称，但 `HistorySeries.schedule()`、`SyncTask.schedule()` 当前没有将这些字段传给 normalizer。入库名称取自详情，尚无按 teamID 核验的历史名称优先级规则。

如果之后选择赛程标签作为历史记录的优先来源，需要单独验证同一 BO、双方不同且为正的 teamID、唯一红蓝映射、非空赛程标签和原件依据；不能只按名称相似度更名。应保留详情标签和冲突审计，并在单局事务中同步 Match 的红方、蓝方及胜方名称，以及 Team、Player 的队名和旧自然键。

名称数据变更会影响战队列表与详情地址、选手队伍筛选、比赛详情和胜方、比较分析、AI 的队伍/对手/胜方范围、实体目录及已有查询上下文。这些变更需独立回放和验证，不与本次说明口径修复混合。
