# AI 分析的战队名称口径

AI 表格中的“来源战队”“对手来源战队”“获胜来源战队”表示每条出场或比赛记录保存的队伍标签。它同时覆盖 ScoreGG 已核验记录和未核验历史导入，不能统一称为“单局详情名称”。来源标签可能与历史赛程名称不同，也不等于已核实的当年正式队名。

查询继续按记录标签分组和筛选，不自动合并历史名称，不通过名称推断官方转会或更名。核验标志证明该记录已通过现有来源校验，不额外证明队名在历史日期的正式身份。

新核验记录只有同时确认同一 BO、双方不同且为正的来源 teamID、唯一红蓝映射、非空且不同的赛程标签，才优先采用赛程名称。未满足条件时保存详情标签；未回放的旧记录保持原名称。查询仍按保存的名称精确筛选，不建立全局 `QG ↔ JDG` 别名。

## 本次修复的依据

一次真实问题查询了 2016 年已核验 LPL 比赛中 Uzi、Xiaohu 按记录战队分组的击杀与 MVP 数据。独立 SQL 对照冻结了 112 局、161 次出场，84 项计数、样本、范围和展示检查全部通过。其中 Uzi 的 20 次出场记录保存为 `JDG`。

这 20 局对应 11 个 BO 系列、9 份已归档阶段赛程。同一 `teamID=28` 在赛程中标为 `QG`，在单局详情中标为 `JDG`。对照确认了双方 teamID、BO 编号、Uzi 星位、击杀和 MVP，以及赛程原件哈希与持久化 `source_json` 的一致性，共 140 项来源关联检查。

例如单局 `436` 属于系列 `197`，赛程日期为 `2016-01-31`；赛程的 `teamID_a=28`、`team_short_name_a=QG`，详情的 `red_teamID=28`、`red_name=JDG`。证据证明两个来源的标签不一致。它没有独立证明当年官方队名、组织继承关系或正式转会日期，不能据此建立全局 `QG ↔ JDG` 别名。

本机验收证据位于忽略的 `artifacts/ai-count-samples-live-benchmark.json`、`artifacts/ai-count-samples-live-projection.db` 和 `artifacts/ai-count-samples-team-label-source-audit.json`。人工 NULL、零值和有效样本边界测试与这次真实查询分开保存；上述真实范围没有 NULL 击杀或 MVP，不能冒充真实 NULL 边界验收。

## 入库与证据

- `Match.team_name_provenance` 保存原始赛程与详情名称、双方 ID、BO、选用来源和明确的核验或拒绝理由。旧数据库新增字段后为 SQL NULL，不伪造旧来源证据。
- 规范化 JSON 的 SHA 与原件文件的 SHA 分别标记；归档链提供实际路径和文件 SHA，纯规范化调用仅提供规范化 SHA。赛程归档是实际包含该行的原件版本，不是 resultlist。每个 `HistorySeries` 保存 `schedule_raw_file` 和 `schedule_raw_sha256`，不将阶段最新文件自动附给被新清单省略的旧 BO。旧空绑定在实际 SHA 和唯一原行校验后补齐。
- Match 的红蓝方和胜方、Team、Player 使用同一名称决定。具备同局身份的旧自然键在单局事务中原位更名，避免互换名称时碰撞；相同昵称的位置保留已核验可选值，不同选手不继承旧位置的数据。完整原件回放仍按其原有 `replace_existing` 口径更新指标。
- 源码只选用经 ID 核对的赛程标签，不声称已核实官方俱乐部身份或沿革。AI 列定义、查询说明和文字解读继续说明这一边界。

例如保存为 `JDG` 的旧出场不会自动纳入 `QG` 筛选。只有该局经过上述来源校验并实际回放为 `QG`，才进入对应查询。空结果不证明现实中没有比赛。模型解读须以当前查询数据为准。

## 回放与部署

历史与每日采集传递完整原始赛程行；未关联旧单局不制造赛程。已有完整或来源残缺单局只有本地原件通过相同身份规则且选用名称改变，才触发名称回填。

部署先按 [迁移说明](TEAM-NAME-MIGRATION.md) 取得同一个采集锁并备份，依次完成两个独立脚本的列迁移，再启用会读取新列的代码。原件回放计划冻结详情文件 SHA、完整赛程行、目录关联及 BO 原件版本；应用前重新核对，来源改变则拒绝该计划。没有可复核赛程文件时不制造文件 SHA，仍冻结并核对持久原行和关联。

名称变更会影响战队列表与详情地址、选手筛选、比赛与比较分析、AI 的队伍/对手/胜方范围及实体目录。仅文字标签不同的候选不等于可修复比赛；必须逐局校验，不批量凭名称猜测。S3 单局 `20233` 的主块 BO 缺失，备用块已有明确 BO，但详情双方 ID `{7,200}` 与赛程 `{7,704}` 冲突，仍必须保留详情标签并记录未解决理由。备用 BO 有效不能覆盖双方身份矛盾。
