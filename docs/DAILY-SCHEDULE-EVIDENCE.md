# 日更赛程来源证据

`daily` 先发现赛程，再把本次读取的完整阶段列表归档到
`data/raw/daily/<run UUID>/stage-0001.json` 等独立文件。所有阶段与清单写入成功后，
才更新系列任务、请求结果列表和导入单局。目录及文件以排他方式创建；新的日更不会覆盖旧快照。
归档失败会保存非成功的运行报告，停止后续结果请求和导入，不把没有证据的采集标成成功。

这些文件是客户端解析后的来源 JSON 快照。编码为 UTF-8，JSON 键排序、两空格缩进，
摘要对应实际落盘字节；它们不是 HTTP 原始响应体，也不声称保存了压缩传输字节或响应头。
阶段文件保持原列表和所有原行，包括本次日期窗口外的比赛。每个读取的阶段只归档一次，
报告不会为每局重复保存完整阶段数据。

运行报告的 `details.schedule_snapshot` 保存目录、清单路径和 SHA、各阶段的官方 URL、
缓存 key、父 round ID、读取时间、候选系列 ID 和阶段文件路径与 SHA。`manifest.json`
在写入阶段文件前持久化计划来源与 `expected_sha256`，方便中途退出后的审计；
清单明确要求核验文件是否存在及其实际摘要，不能仅凭计划清单认为快照完整。
只有运行报告中快照的 `status=complete` 表示所有归档成功。本次归档失败时为 `incomplete`，
已写文件及计划仍保留，报告中的实际错误不被吞掉。

每条处理结果的 `schedule_evidence` 记录必要的来源定位、系列与赛事 ID、开赛时间、
原 `status`、`is_publist`、双方比分及原行的 canonical SHA。该 SHA 使用现有队名证明相同的
UTF-8、键排序、无多余空白编码。可以在对应阶段文件中定位并核验唯一原行。
`source_archive` 同时传给原有队名规则，使新导入的证明能指向真实归档。
赛程状态和发布标志分别保留；缺少 `is_publist` 仍为未知，比分不能推导出战报已发布。
读取时间也不冒充源站的发布时间，实际来源存在的其他字段完整留在阶段原行中。

同一 BO 在不同阶段重复出现时，只比较赛事身份、开赛时间、双方 ID 和短名、
比分、比赛状态、战报发布标志及多队标记。双方 ID 均明确且不同的 A/B 换位按 ID 对齐；
图片、标题、直播链接等展示字段差异不会阻止采集。等价重复沿用已有的来源选择顺序，
两份完整阶段来源仍归档。业务值冲突、跨不同赛事引用同 BO，或同一阶段重复同 BO，
则记录发现错误并停止处理该 BO；后续再次出现也不会消除已发现的冲突。
其他无冲突系列继续按原有日更规则处理，运行保留 `partial`。
对已选中的 BO，该核验包含本轮实际读到的所有同 BO 原行，即使另一行日期在明天或窗口外。
不相关的窗口外 BO 不会由此进入任务范围，也不会追加阶段请求。

快照完成后如果结果列表或单局请求达到请求/时间预算，运行仍保留完整快照与实际 SHA，
并沿用 `budget_exhausted` 和已开始任务的 `queued` 状态，方便续批；不会把预算中断误称为归档失败。

本改动不迁移数据库、不增加来源请求，也不修改完赛 404、明确 pub0、待赛或进行中的任务语义。
旧 `retry` 任务没有原赛程证据时继续保持未知，不凭任务编号制造来源快照或发布状态。
