# 查询数据先展示，再完成文字解读

AI 助手仍按「受控业务计划 → 实体解析 → 可信查询编译 → 同一只读快照 → 结果解读」执行。首页收到查询结果后立即显示数据、有效样本、图表和统计口径，文字解读随后更新。解读不可用时保留已完成的数据和确定性摘要，不能将数据查询误报为失败。

原 `POST /api/ai/query` 继续返回完整 JSON。首页使用新的 `POST /api/ai/query-stream`，请求字段仍为 `prompt`、可选 `context`，返回 `application/x-ndjson`。两个入口共用查询与解读服务；不通过客户端提交结果行进行解释，也不在解读时重查数据库。

事件顺序：

1. `data` 携带完整 `result`，包括确定性摘要、数据、证据和后续问题。
2. `explanation` 携带该快照的最终 `result`；仅在实际尝试文字解读时发送。
3. `done` 表示当前请求结束。

`result.explanation_status` 为 `pending`、`complete`、`unavailable` 或 `skipped`。缺项、空结果、澄清、明确不支持的问题和已经用完修复额度的查询，不再请求文字解读。请求可指定 `explain: false`，保留查询数据与确定性摘要；它不能跳过必要的计划调用。

输入、密钥、计划和 SQL 的预期错误在首块发送前沿用 JSON HTTP 错误码。开始发送后的预期错误使用 `error` 事件；客户端保留已经收到的数据，提示解读未完成。不能把缺少 `done` 的断流当作解读成功。

每个问题最多两次模型调用。计划或目录兼容修复已经占用第二次时，跳过文字解读。模型服务仍使用现有超时，没有增加付费重试。客户端取消请求不能保证中断已经发出的同步模型调用；关闭后端生成器且尚未开始解读时，不继续启动解读。

`evidence.timings_ms` 记录实际执行阶段，单位为毫秒：`catalog` 实体目录与候选、`planning` 第一次模型规划、`repair` 计划修复、`compile` 查询编译、`query` 同快照 SQL、`writer` 文字解读、`data_ready` 从服务开始到数据就绪、`service` 当前服务总耗时。多次执行的修复、编译和 SQL 阶段累加；未执行的阶段为 `null`。`service` 不包含请求进入服务之前的 Waitress 排队和浏览器传输时间，流式结束值也包含生成器恢复执行的等待。

此前真实 QG 问题用时 43.439 秒，SQL 计时 16 毫秒、两次模型调用；没有各模型阶段计时，不能据此断言是文字解读或网关导致。流式改动改善数据可见时间，不能消除第一次规划等待，也不会减少已启动解读占用的 Waitress 工作线程。

回归使用临时数据库和受控模型，覆盖第一块早于解读完成、解读失败保留数据、同快照不漂移、调用额度和断流。`tests/test_ai_waitress.py` 通过真实本机 HTTP 和 Waitress 验证首块没有等待解读：收到数据后并发插入另一场比赛，最终解读仍使用原查询快照。该测试没有调用真实模型，不能作为 DeepSeek 各阶段耗时的证据。
