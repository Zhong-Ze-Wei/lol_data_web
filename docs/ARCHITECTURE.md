# 从三个目录到一条流程

旧目录共享 ScoreGG 数据，但各自保存了采集、导入和展示逻辑，格式与更新时间并未统一。

| 原目录 | 原职责 | 统一后的职责 |
| --- | --- | --- |
| `lol爬虫` | 抓取单局 JSON、导出选手/战队 CSV、写 MySQL | `app/services/spider.py` 发现赛程，`ingestion.py` 验证与入库，`scripts/pipeline.py` 编排 |
| `lol_data` | Flask API、Vue 网站、AI 数据问答 | `app/` 查询与分析 API、`frontend/` Vue3 网站，延续原 Git 历史 |
| `lol_data_show` | 清洗 CSV、五位置雷达、Notebook/Spark 实验 | `app/services/analytics.py` 同位置统计，网站分析与详情图表；Notebook 保留本机档案 |

交集是同一来源的单局、战队和选手出场数据。普通 CSV 有完全重复的副本；不同 S13 文件也有大量重复。文件更多不代表覆盖更多比赛。旧 CSV 混有不同列数、无效时长和自然键冲突，且没有可靠的游戏类型、英雄与开赛日期证据。

统一流程只维护一套业务模型：赛程发现 → 保存来源 JSON → 验证 LOL 与单局结构 → 规范化 → 事务入库 → API → 网站与分析。历史导入也进入这套模型，附带未核验标记和问题报告。

## 标识与数据范围

ScoreGG 的系列赛 `matchID` 与单局 `resultID` 不是同一个编号。数据库 `matches.match_id` 延续旧接口约定，保存单局编号；`series_id` 保存系列编号。完整的一局对应两条战队出场和十条选手出场。

来源明确的在线数据标记 `verified=true`。旧 CSV 标记 `source=legacy`，不能因为导入成功就认定属于 LOL、比赛完整或日期准确。来源明确证明不是 LOL 时，只移除未核验的旧衍生记录，原始 CSV 和审计仍保留。

`verified` 验证的是公开来源与游戏类型，不代表全部指标完整。已发布历史战报可能缺时长、昵称或数值；缺项保留 NULL，持久任务标记 `source_incomplete`。完整单局必须具备大于1秒的合法时长、两条战队出场和十条选手出场，且没有识别出的必要缺项或非法指标。历史 `00:00 / 00:01` 占位及非法分秒明确清空三张表的业务时长，不保留旧值作为分母。第一次以官网来源覆盖旧数据时，官网缺项也覆盖为 NULL，不能混用旧 CSV 的值制造已核验指标。历史可选百分比无效时定点清空并保留原值与原因，不能被旧值保护逻辑填回；日常严格校验保持有效。

历史来源少一个昵称时，`ingestion.py` 保留可靠比赛、双方与其余已知选手，移除缺槽原有的猜测身份及战队名单引用。`source_identity.py` 离线扫描归档，只有星位和来源名单中的选手 ID、颜色唯一对应，且该 ID 的已知昵称没有冲突时，才提供恢复候选；报告保存原件路径、字段和 SHA。重放前复核目标及依据原件的 SHA，不猜数组顺序或别名。原始响应不修改，部分阵容与可靠的十人阵容仍按实际质量分别统计。

旧来源没有统一缺项标志，`ingestion.py` 通过有限的跨层矛盾判断整组统计是否未记录：原始十槽击杀必须与各自战队汇总一致、总击杀大于0、胜负已定；十人伤害/承伤及双方伤害全为明确0时排除伤害族，十人及双方经济全0时排除经济族，经济族满足条件且十槽补刀全0时再排除补刀族。只清对应族中来源明确为0的字段，并保存结构化字段、原值和战果证据；清NULL与单局入库处于同一事务，覆盖旧值保护但可整体回滚。缺键、NULL、无效未具名槽资料或击杀汇总冲突取消对应判断，不因单人0扩大清空；插眼、等级与塔龙等不在规则中。十槽统计证据不要求十个具名业务行，也不制造缺失身份。

正常时长的日更战报遇到上述缺项时保存可靠部分，状态为 `source_incomplete`；每日窗口内仍会重取详情，后续补齐可恢复。严格日更缺时长保持待处理。比赛详情说明缺失伤害、经济和补刀，全部伤害为NULL时不画零伤害图，真实0保留。

日期分析只使用 `Match.date_source=schedule` 的赛程日期。`updated_at` 仍保留为来源档案，但不会参与年度、日期筛选与月趋势。选手表和战队表的旧日期不能绕过这个约束。

雷达比较同位置、同日期区间内达到最低场次的选手，展示六项指标的百分位。缺失值保留为空；承伤占比表达打法，不能作为实力总分。旧 Spark 实验用的是赛后指标，保存在研究档案中。

`stat_metrics.py` 统一分均公式：逐局已知非负总量×60÷ `Match.game_time` 的完整秒数，再取均值；时长缺失或不大于1秒的出场不参与。AI 查询、单条 DTO、档案均值、雷达与月趋势使用同一口径，各指标独立计数有效样本，不采用总量之和除以时长之和。选手和战队出场只关联唯一的比赛记录，避免样本倍增。raw 保留完整来源原值；业务行仅将有证据的异常字段置空。分均插眼因缺少可信总量，保留来源整数精度并声明限制。选手明细日期取关联比赛的确认赛程，不能使用选手表旧日期冒充开赛日期。具体异常和校正记录见 `DATA-QUALITY.md`。

## 运行与保存

- GitHub 保存代码、依赖锁文件、测试、自动构建和文档。
- 本机 `data/` 保存数据库、来源原件、迁移报告和备份；每天运行同一个采集 CLI。
- Windows 任务需要当前用户已登录、电脑开机联网；错过计划时可在恢复条件后补跑。
- 每次运行有单实例锁、请求/时间预算、持久任务状态与非零失败退出。来源没有新数据时不会伪造最近更新时间。
- 原三个目录保留，便于对照与回滚；日常运行入口为 `lol-data`。

全历史补采由 `HistoryTournament`、`HistoryStage`、`HistorySeries` 与 `SyncTask` 记录目录及各层游标。官网目录日期未知的赛事同样保留。每批有请求和时间上限，连续执行器重复调用同一个 CLI，从持久状态续批；HTTP重试也遵守最小间隔。待发布、来源缺项、请求失败和失败耗尽分别显示，预算耗尽不是采集失败。

执行器运行状态与持久任务完成状态分开。每次启动生成新会话，区分当前批次与上次完成批次，使用标准库线程每15秒保存心跳；状态和心跳写入由同一锁串行化并原子替换。正常收尾先停止心跳线程，再写停止、失败或本轮审计完成状态。API只读检查带时区的心跳，90秒内且会话仍在运行才判为活跃；过期、未来时间和旧文件缺少心跳都不判活跃，不依据陈旧的 `continue` 或数据库 `running` 推断进程存活。每日让出、锁等待和重试等待仍持续心跳，但页面分别说明等待原因。强制终止通过心跳过期识别，不能保证立即发现。

批次调度先检查到期可运行任务，再检查当前快照是否审计结束。快照可以保留待发布或来源缺项，因此恰在批次收尾到期的待发布任务仍须续采，不能仅凭快照标志退出。

首页每30秒只读刷新进度，刷新时保留上一份已显示数据；本地每15秒以API返回的心跳年龄及收到响应后的单调经过时间重判活跃状态。即使下一次请求挂起，旧心跳也会过期；离开页面时清理定时器并取消请求。

离线校正先保存完整的逐项before/after计划及原件SHA，再逐局原子执行。每局结果追加短JSONL，结束时写最终完整报告；不再为每一局反复重写整批证据。中断时仍有初始计划和已执行记录，原件不修改。

GitHub CI 使用临时测试数据库验证代码；本机每日采集和历史补采更新同一个持久数据库。提交代码不会把本机数据库、原始响应或个人 AI 密钥发布到 GitHub。

## 数据问答

模型生成受控 JSON 计划，业务目录维护允许的对象、指标、维度、公式与粒度。实体解析使用实际数据库和可审核的英雄别名；歧义给出候选。查询编译器只选择明确的单局关联，不把选手和战队出场关联成笛卡尔倍数。

一次只读查询同时读取统计和范围证据。结果包含指标值、有效样本、来源核验和日期质量，模型在这些结果基础上解释。正常至多两次模型调用；一次计划或字段修复占用第二次调用，并改用确定性摘要。网络失败不自动重新付费，查询已成功时仍可展示数据。

DeepSeek模型调用附加原生 `thinking: {"type": "disabled"}`，同时保留网关 `enable_thinking=false`；其他模型不附加该原生参数，默认2048输出预算不增加。解读提示要求最多三条短句、合计不超过200字，避免重复结果表。长度超限仍按不可用处理，数据查询不回滚；失败日志仅记录本地固定错误文案，不打印鉴权头、密钥或响应正文。

追问携带上一有效计划，不能传入任意历史 SQL。只读单语句检查、表范围、条数和执行超时继续约束最终查询。新增分析角度先加入业务目录与可手算回归，再开放给模型。业务取舍和真实验收分别记录在 `DESIGN-DECISIONS.md` 与 `AI-EVALUATION.md`。
