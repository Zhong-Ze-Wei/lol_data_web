# 采集状态反馈

顶栏区分单批采集记录与后台执行器的近期心跳。`SyncRun.status=running` 表示这条批次记录尚未收尾，不能单独证明进程仍在运行；`budget_exhausted` 表示本批请求预算用尽，后续任务可以由下一批继续处理，也不表示全部历史已经补齐。

`GET /api/sync/status` 保留既有字段，新增 `history_worker`。它复用 `/api/sync/history` 已有的 `worker_status` 安全字段清单，公开会话、阶段、批次与心跳信息，不返回 PID、密钥或任意运行配置。接口仍只读，不启动采集、不写任务或数据库。

只有 `alive=true`、心跳状态为 `fresh`，且心跳年龄仍在接口返回的有效期内，顶栏才显示“历史补采进行中”。当前执行器每 15 秒更新心跳，有效期为 90 秒；这是近期存活证据，不能立即发现被强制结束的进程。过期、未来时间、缺失或无效心跳均不能推断仍在运行。

以下阶段保留存活证据，但顶栏明确显示等待，不显示采集进行中的标记：

| 后台阶段                    | 顶栏反馈                     |
| --------------------------- | ---------------------------- |
| `daily_pause`               | 历史补采等待每日采集窗口结束 |
| `locked`                    | 历史补采等待其他采集任务结束 |
| `retry_later`、`retry_wait` | 历史补采等待重试             |

每日发现阶段达到分配预算时，现有采集器也可能保存 `partial` 批次。只有返回的 `details.discovery_limited=true`、`discovery_errors=[]` 且本批 `failed=0` 时，顶栏将它解释为“本批发现预算已用尽，后续待补采”，不显示失败；未知原因的 `partial` 仍保留核查反馈。实际发现错误不会因同时达到预算而被掩盖。

已有失败批次、部分失败、明确失败任务或后台错误仍显示失败反馈。下一批正在运行不会掩盖这些已返回的失败信息。这里沿用 `/status` 的批次及单局任务口径；完整历史目录各层级的失败数量仍以 `/api/sync/history` 覆盖报告为准。

顶栏每 30 秒只读刷新一次状态，已有请求未完成时跳过轮询，卸载时取消请求并清理计时器。页面每 15 秒重新计算心跳年龄，以最后一次成功响应对应的请求起点作为单调时钟锚点，将整次请求耗时保守计入心跳年龄。延迟送达的旧响应不会重新获得完整有效期；新请求挂起时也不会重置缓存状态的有效期。正常刷新期间保留上一份状态与已收录数据范围；请求失败显示“采集状态暂不可用”并撤下运行标记，直到下一次成功读取才清除该反馈。

“采集状态更新”记录浏览器最近一次成功读取状态的时间，以香港时间显示。它不是比赛数据完成时间，也不把批次开始时间当成数据更新时间。刷新失败时保留上一次成功读取的时间，不声称当前读取成功。

本次验证使用临时 SQLite、模拟运行状态文件和前端时钟/请求夹具，覆盖第 38 批运行、等待、预算续批、失效心跳、失败优先反馈、长挂页面及卸载清理。组件回归还覆盖失败后的下一请求挂起、成功恢复，以及已生成的近期响应延迟 120 秒才送达。真实网站部署与浏览器验收由集成阶段执行。

历史补采进度面板读取 `/api/sync/history`，沿用同一心跳判定：只有明确的近期存活证据才显示正在补采。最后一次成功响应对应的请求起点作为单调时钟锚点，整次请求耗时计入心跳年龄；等待新响应不会延长旧缓存的有效期。每 30 秒只读刷新，已有请求尚未完成时跳过轮询，卸载时取消请求并清理计时器。

进度读取失败后保留上一份覆盖统计，显示“历史补采进度暂不可用”和“后台运行状态暂不可用”，撤下正在补采及当前批次的声明。下一次请求挂起时仍保留不可用提示，只有成功响应才能恢复状态和更新统计。逐年进度、源缺项、待发布、失败任务及日期口径保持原定义；缓存统计不表示刚完成了采集。
