# 采集时的赛程身份检查

公开详情的 gameID、选手数据已核验，不代表给它附加的赛事和日期也正确。BO15481 的本地赛程曾归属2017 LCL、双方ID1987/200，而28972/28973两份详情明确声明 BO15481、双方ID7/208；此前队名规则回退到详情名称，却仍接受了错误赛程的日期和赛事。

`normalize_result` 现在在时长和胜方校验完成之后、日期和赛事赋值之前，对显式字典 `source_row` 检查已知身份矛盾：

- 详情声明的 BO、`schedule.series_id`、原行 `matchID` 中，任意两个明确的正整数不同。
- 详情或赛程完整的双方ID重复；两组完整ID不一致；一组完整时，另一组已有的ID不在该组双方中。
- 详情双方ID完整时，辅助 `result_list.teamID_a/b` 的已知ID不属于双方，或完整辅助双方重复。

已知ID采用 ASCII 正整数字符串/整数语义。缺键、空值、0、负数及不能识别的字段不补成ID，也不自行构成新冲突；已有详情 BO 格式与主/辅 BO 冲突校验照常执行。检查独立读取原字段，不依赖队名证明的 `reason`，所以缺BO或队名不能遮住另一个已知的队伍冲突。

发现明确矛盾会抛出已有 `InvalidResult`。`ingest_result` 沿用现有失败处理与回滚：已有 Match、Team、Player 的全部字段、主键和自然键保持；本次任务记为 failed，并保留重试时间。SyncTask 的赛事、日期等元数据仍可由 `get_task/start_task/finish_task` 记录本次尝试，不能把业务三表的保护承诺延伸到任务元数据。

缺少字典原行的旧 backfill/retry、只有备用 BO 的合法详情、没有明确冲突的缺项继续兼容。严格模式00:00/00:01时长占位仍先判 pending；历史宽松时长模式也不能越过明确身份冲突。队名的展示回退与 `resolve_team_names` 规则保持原状。

这项检查阻止后续错误关联，不修复已有错挂数据，不根据队名猜别名，也不证明赛程日期与其它未声明字段正确。已存的错误关联需要独立来源审计和显式修复。

验证用28972/28973的真实 BO、双方ID、胜方、时长及两份赛程身份投影，原详情SHA分别为 `7924c0b228179e5e8882a08288358da2375962aa7939f34783a49647a2b50ee0`、`6990f68a23befee26ca0430e33555449955d75d7b9b9c2a4ccc97878f7956c0f`。其它数值取公开66845测试fixture，不冒充原两局指标。临时SQLite文件测试逐字段比较已有三表，验证失败只计一次、自然键不增长与输入原件不变。所有测试离线运行，不访问生产库。
